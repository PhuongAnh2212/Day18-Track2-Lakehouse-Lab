01 · Problem Statement

The hard problem is not search. It is reproducible scientific retrieval.

Imagine a neuroscience platform containing 2 million fMRI sessions across hospitals, labs, and public datasets. Each session may include raw BOLD time series, anatomical MRI, task descriptions, behavioral logs, preprocessing outputs, brain-region activation maps, clinical metadata, consent constraints, and published paper links.

Researchers want to ask: “Find studies where working-memory load increases frontoparietal activation in adolescents, but exclude scans processed with outdated motion-correction pipelines.” A normal vector search system cannot safely answer this unless it knows exactly which subject cohort, brain atlas, preprocessing pipeline, statistical threshold, embedding model, and document version produced each retrieved result.

02 · Core Insight
Multimodal RAG for fMRI is a data governance problem before it is an LLM problem.

The system must retrieve across text, images, time series, brain atlases, cohort metadata, and analysis outputs. But the answer is only trustworthy if every retrieval can be traced back to its exact source: subject/session ID, consent scope, preprocessing version, atlas version, chunk version, embedding version, and index version.

A good design therefore separates the lakehouse source of truth from the low-latency retrieval service. The vector index serves search. The lakehouse proves what was searched.

03 · Why fMRI RAG is uniquely difficult

Brain data breaks the assumptions of ordinary document RAG.

1. The same scan can produce different truths

Motion correction, smoothing, normalization, and statistical thresholding can change the apparent activation pattern. A retrieval result must include the preprocessing pipeline that produced it.

2. The data is multimodal by nature

A session is not one document. It may contain BOLD time series, anatomical MRI, task design, event timing, behavioral scores, clinical notes, atlas mappings, and derived activation maps.

3. Cohort filtering is not optional

Age, sex, diagnosis, handedness, scanner type, task protocol, and site effects may determine whether a result is scientifically valid. Retrieval must combine semantic similarity with structured filters.

4. Privacy and consent shape the architecture

Human brain data can be sensitive. The system must enforce consent boundaries, de-identification, access control, and audit logs before any researcher or LLM sees protected metadata.

5. Embeddings will change

Text, image, time-series, and graph embeddings will improve. The design must support multiple embedding generations without overwriting historical retrieval behavior.

6. Scientific citations require reproducibility

If a paper cites a retrieved cohort or activation pattern, the system must reproduce that exact result years later, even after new preprocessing and embedding models are introduced.

05 · Key Architecture Decisions

Every choice must reject tempting alternatives.

Decision 1 — Table Format

I chose Delta Lake as the primary lakehouse table format for Bronze, Silver, and Gold metadata tables.

Rejected plain Parquet because it lacks ACID transactions, time travel, and reliable rollback during reprocessing.

Rejected vector-store-only storage because a vector DB can serve retrieval but cannot prove scientific lineage across preprocessing, atlas, and cohort versions.

Decision 2 — Storage Layout

I chose Bronze → Silver → Gold because each layer answers a different trust question.

Rejected storing only derived features because researchers may need to reprocess raw scans with improved pipelines.

Rejected storing only raw scans because every query would become too slow and expensive.

Decision 3 — Retrieval Strategy

I chose hybrid retrieval: structured filters first, multimodal vector retrieval second, reranking third.

Rejected vector-only retrieval because fMRI questions often require exact cohort, scanner, atlas, task, and diagnosis constraints.

Rejected SQL-only retrieval because semantic questions about cognitive constructs and brain networks need similarity search.

Decision 4 — Embedding Lifecycle

I chose append-only embedding versions where every vector stores modality, model, preprocessing, chunking, and index versions.

Rejected overwriting embeddings because old retrieval results would become impossible to reproduce.

Rejected one global index because text, image, graph, and time-series embeddings may need different models and refresh cadences.

Decision 5 — Governance and Privacy

I chose tokenization at Bronze landing and audit logging for every sensitive metadata read.

Rejected downstream-only masking because raw identifiers could leak before the governance layer is applied.

Rejected unrestricted researcher access because consent scope and human-subject privacy must be enforced at query time.

Decision 6 — Brain Representation

I chose atlas-aware region summaries plus raw-derived links for retrieval.

Rejected only full 4D image embeddings because they are expensive, hard to interpret, and difficult to cite.

Rejected only text descriptions because they discard spatial and temporal brain signals that are central to fMRI.

06 · Gold Retrieval Object

The retrieval row must carry scientific provenance.

Field Purpose
retrieval_object_id Stable identifier for a text chunk, activation summary, image descriptor, or time-series feature.
subject_token, session_token De-identified links to the human participant and scan session.
modality Text, anatomical MRI, BOLD time series, activation map, behavioral log, table, or paper.
pipeline_version Exact preprocessing workflow used to create the derived object.
atlas_version Brain parcellation used for region-level interpretation.
chunking_version Chunking or feature extraction logic used before embedding.
embedding_model_version Model used to create the vector representation.
index_version Vector index snapshot used by production search.
consent_scope Controls whether the object can be used for research, clinical review, teaching, or external sharing.
07 · Query Path

Every user question becomes a retrieval plan.

1. Parse intent

Identify cognitive construct, brain regions, population, diagnosis, modality, and required evidence type.

2. Apply hard filters

Filter by consent, cohort, scanner, age group, diagnosis, task design, atlas, and pipeline version.

3. Retrieve semantically

Use modality-specific embeddings for papers, notes, activation maps, time-series summaries, and tables.

4. Rerank with provenance

Prefer results that match the query and have strong quality-control, clear citations, and stable preprocessing metadata.

5. Answer with evidence

The final answer cites document/session versions, brain atlas, statistical threshold, and embedding/index versions.

08 · Failure Modes

What breaks at 3 AM?

Failure 1 — New preprocessing pipeline changes activation patterns

Detection: Golden queries show changed region-level evidence or unexpected activation distribution shifts.

Rollback: Use lakehouse time travel to restore the previous Silver/Gold version. Keep the old index active until the new pipeline passes scientific validation.

Failure 2 — Embedding upgrade reduces retrieval quality

Detection: Evaluation set shows lower recall for known neuroscience queries or more citation mismatches.

Rollback: Do not promote the new index version. Continue serving the previous embedding/index pair.

Failure 3 — Consent filter bug exposes restricted data

Detection: Audit logs show query results containing objects outside the user’s approved consent scope.

Rollback: Disable affected index, rotate access tokens, replay audit logs, and rebuild Gold retrieval objects with stricter governance tests.

Failure 4 — Vector index becomes stale

Detection: Gold table contains retrieval objects with a newer index_version than the vector DB.

Rollback: Serve the last healthy index while rebuilding the new index from the Gold table snapshot.

Estimated starting production cost: $6K–$18K/month. The biggest cost risk is not storage; it is repeated preprocessing and embedding regeneration. This is why versioned incremental refresh matters.

10 · One-Week MVP

Build the smallest slice that proves the hard part.

Scope

Ingest 1,000 open fMRI sessions or synthetic BIDS-like records, plus associated papers/task descriptions. Store raw metadata in Bronze, standardized tables in Silver, and retrieval objects in Gold.

Hard part to prove

A query must return an answer with session ID, document version, preprocessing version, atlas version, embedding version, and index version.

MVP Success Criteria

Requirement Pass condition
Multimodal retrieval Search across task descriptions, papers, activation summaries, and cohort metadata.
Structured filtering Filter by age group, task, atlas version, pipeline version, and consent scope.
Reproducibility Re-run the same query against the same index version and recover the same evidence set.
Rollback Demonstrate restoring a previous Gold table version after a bad embedding refresh.
Auditability Every answer includes source evidence and provenance fields.

12 · Final Position
For human brain fMRI data, the winning architecture is not the one that retrieves the fastest. It is the one that retrieves with proof.

The lakehouse preserves scientific truth. The vector index accelerates discovery. The RAG layer explains evidence. Together, they create a system that can support neuroscience research without losing reproducibility, privacy, or trust.
